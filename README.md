# Clossify

네이버 스마트스토어 상품 자동등록 **로컬 MCP 서버**. 사용자 사진과 최소 정보에서
출발해 상세페이지 생성 · 상품명/SEO · 상품정보제공고시 작성 · 커머스 API 등록까지
한 흐름으로 잇는다. 서버 호스트는 없고, 자격증명은 사용자 PC의 설정 파일에만 있다.

> **게이트 정책**: 결정론 검사는 등록 직전 FAIL 위반을 차단한다(fail-closed).
> LLM 판단이 필요한 카피/이미지 QA는 `prepare_listing` 경로에서 PENDING 으로
> 등록되고, 집계 게이트(`qa_agents.qa_gate`)는 PENDING 도 차단하므로 미회신이면
> 등록이 막힌다. 클라이언트는 `submit_reviews` 로 회신하며, 회신은 서버 판정과
> **최악값 병합**(FAIL > PENDING > WARN > PASS)이므로 서버 FAIL 을 뒤집을 수
> 없고, 결정론 검사(`compliance`)는 제출 자체가 거부된다. `register_product` 를
> 직접 부를 때 prepared 기록이 있으면 완전 게이트(PENDING/FAIL 차단), 없으면
> 결정론 검사만 적용하고 응답의 `gate` 필드로 그 사실을 표기한다. 도구 회선과
> 집계 게이트의 차이는 `docs/ARCHITECTURE.md` 참고.


## 다음 단계는 법인 설립이다

**여기서 기능을 더 만드는 것보다 법인을 먼저 세우는 것이 맞다고 판단한다.**
지금 더 만들어도 법인 설립 후 조건이 달라지면 **다시 만들어야 하기 때문**이다.

구체적으로 아래가 법인 여부에 따라 달라진다.

**1. 배포 경로가 자격에 걸린다**

네이버 커머스 API 를 제3자에게 제공하는 경로는 두 가지인데, 그중 `API대행사` 는
**국내 법인 사업자가 필수**다(개인·해외 사업자는 반려). 나머지 하나인 `커머스솔루션` 은
자격 제한이 없지만 **사업자 서버에서 호출하는 구조**라 지금 같은 로컬 실행 도구는
해당하지 않는다.

즉 이 도구를 **나 외의 판매자에게 제공하려면** 법인이 전제다. 그 구조를 모르는 채로
배포·인증·과금 계층을 만들면 경로가 정해진 뒤 대부분 다시 만들게 된다.

**2. 판매자 정보가 규제 신고값으로 상품에 실린다**

제조사·A/S 책임자·연락처 같은 값이 상품정보제공고시에 **그대로 신고**된다.
지금은 개인 명의로 들어간다. 법인이 되면 이 값들이 전부 바뀌고,
이미 등록된 상품의 신고값도 갱신 대상이 된다.
템플릿·기본값 설계를 지금 굳히면 그때 다시 손봐야 한다.

**3. 저작권자·라이선스 주체가 바뀐다**

현재 저작권자는 개인 명의다. 법인 설립 후에는 저작권자와 기여자 동의서(CLA)의
주체가 달라진다. 라이선스 구조를 지금 확정해도 다시 정리하게 된다.

**4. 계정·자격증명의 귀속이 바뀐다**

스토어와 API 자격증명이 개인 계정에 묶여 있다. 법인 이관 시 인증·권한 구조가
달라지므로, 그 위에 얹는 다계정·위임 설계는 지금 만들 이유가 없다.

---

**그래서 다음 순서는 이렇다.**

1. 법인 설립
2. 배포 경로 확정 (`API대행사` / `커머스솔루션` 중 어느 쪽인지)
3. 그 경로가 요구하는 구조에 맞춰 인증·배포 계층 설계
4. 그 다음에 기능 확장

**지금 단계에서 더 쌓는 것은 되돌릴 가능성이 높은 작업이다.**
현재 상태를 여기서 고정하고, 법인 조건이 정해진 뒤 이어간다.

## 어떻게 쓰는가(개념)

MCP의 UI는 자연어다. 사용자가 "이 사진들로 등록해줘"라고 말하면, 클라이언트 LLM이
아래 도구를 호출한다. 서버는 검증하고 부족한 값이 있으면 무엇이 필요한지 되묻는다.

**전형 흐름**: 사용자가 상품명·가격·사진(로컬 파일 또는 URL)을 건네면, 클라이언트는
`prepare_listing` 으로 이미지 정규화·상세페이지 조립·QA 집계를 한 번에 수행한다.
서버는 JPEG 비의존 QA는 바로 실행하고, 이미지/카피 품질처럼 LLM 판단이 필요한
항목은 PENDING 으로 돌려 needs_llm 에 담아 who-asks-what 을 알려준다. 클라이언트가
판단을 내려 `submit_reviews` 로 회신하면 PENDING 이 해소되고, 부족한 고시 값은
사용자에게 되물어 보완한다. 게이트를 통과하면 `register_product` 가 커머스 API 로
실제 등록을 하고 그 결과를 돌려준다. 등록된 내용을 네이버에서 다시 읽어 확인하려면
`get_product` 를 **따로 호출**한다(등록 도구가 자동으로 재조회하지는 않는다). 요약하면 **사진을 주면 → 부족한 값을
되묻고 → 확인 후 등록** 된다. 상세페이지 조립 결과는 편집 가능한 구조 문서로도
같이 산출되며, 스펙은 `docs/scene-schema.md`.

### 도구

| 도구 | 역할 | 외부 API 호출 |
|------|------|---------------|
| `check_config` | 설정 파일 존재·필수 키·플레이스홀더·원산지 설정 여부 검사(값 미노출). `read_existing=True` 면 기존 상품에서 정책값을 읽어 제안(온보딩) — 제안만 하고 파일을 쓰지 않는다 | 기본(`read_existing=False`) 없음. `read_existing=True` 시 네이버 커머스(읽기) |
| `upload_images` | 로컬 이미지 경로 리스트를 검증 후 네이버 이미지서버에 업로드 → CDN URL 반환 | 네이버 이미지서버(쓰기) |
| `register_product` | 상품 정보를 받아 페이로드 빌드 → 컴플라이언스 게이트 → 네이버 커머스 API 등록 | 네이버 커머스(쓰기) |
| `get_product` | 등록된 상품(origin product)을 조회(재검증용) | 네이버 커머스(읽기) |
| `delete_product` | 등록된 상품(origin product) 단건을 영구 삭제. `confirm=True` 가 명시적으로 전달된 경우에만 수행한다(되돌릴 수 없는 파괴 동작). 숫자가 아닌 상품번호나 누락은 네이버 호출 없이 거부한다. 삭제 성공 시 로컬 등록 기록(registration_record.json)도 함께 정리한다 | 네이버 커머스(쓰기/삭제) |
| `prepare_listing` | 상품 정보 + 이미지 소스로 등록 전 준비: 이미지 정규화, 상세페이지 렌더, JPEG 비의존 QA 집계 후 prepared payload 저장. LLM 판단이 필요한 항목(needs_llm)과 사용자 입력이 필요한 항목(needs_user)을 알려준다 | 네이버 이미지서버(쓰기) — 로컬 파일을 받으면 업로드한다. 커머스 API 는 호출하지 않는다 |
| `submit_reviews` | 클라이언트 LLM 의 카피/이미지 QA 판단을 prepared payload 의 QA 기록에 병합. 회신은 서버 판정과 최악값 병합(PENDING→PASS 만 허용, 서버 FAIL 불가)이며 compliance 제출은 거부된다 | 없음(prepared payload 갱신만) |
| `manage_products` | 등록 후 관리 — 한 도구에 4동작: 목록 조회(패널용 HTML 포함) · 판매중지 · 판매재개 · 검수 감시. 중지/재개는 `confirm=True` 가 명시된 경우에만 실호출하고, 대상은 등록 기록의 표식으로만 특정한다(추측 금지). 필드 수정(가격·재고)은 이 도구에 없다 — 미실측이라 2차 | 네이버 커머스(읽기 + 상태변경 쓰기) |

## 이렇게 말하세요

이 도구들은 버튼이 아니라 말로 쓴다. 아래는 **실제로 통하는 말**이고, 각각 무슨 일이
일어나는지 같이 적었다.

### 처음 한 번

> **"클로시파이 설정 제대로 됐는지 확인해줘"**

자격증명과 필수값이 채워져 있는지 검사한다. 값 자체는 화면에 찍지 않는다.

### 등록하기

> **"C:/photos/후드티 폴더 사진들로 '겨울 기모 후드티' 등록해줘. 가격 39000원."**

순서대로 이렇게 된다:

1. 사진이 네이버 이미지서버로 올라간다 (이미 네이버 CDN 주소면 그대로 쓴다)
   - 자기 서버·FTP 에 올려둔 이미지 주소를 쓰려면 그 호스트를 먼저 허용해야 한다.
     외부 주소 내려받기는 **기본이 꺼져 있다**(`CLOSSIFY_IMAGE_FETCH_ALLOW_HOSTS`).
     아무 주소나 내려받게 두면 서버가 공격 통로가 되기 때문이다
   - **`ftp://` 주소는 직접 지원하지 않는다.** 평문 자격증명을 이 서버가 들고 있게
     되고, 위의 허용호스트 설계와도 어긋나기 때문이다. 두 갈래로 우회한다:
     ① 대부분의 이미지 FTP 는 **HTTP 로도 서빙**된다 → 그 http(s) 주소를 쓰고
     호스트를 위 환경변수에 등록한다(추가 코드 없이 현행 경로로 커버된다).
     ② 순수 FTP 뿐이라면 **범용 FTP MCP 서버를 함께 붙여** 모델이 먼저 로컬로
     내려받게 하고, 그 로컬 경로를 건넨다(작업 디렉터리 안이어야 한다).
2. 상세페이지가 조립되고 검사가 돌아간다
3. **부족한 값을 되묻고 거기서 멈춘다** — 알아서 채우고 넘어가지 않는다
4. 준비가 끝나면 **미리보기 HTML 파일**이 만들어진다(아래 '미리보기로 한 번 더
   확인' 참조). 브라우저로 열어 상품명·가격·판매상태·이미지·상세페이지·고시 정보를
   스토어 화면처럼 확인할 수 있다

원본 사진이 한 장도 없으면 아예 진행하지 않는다.

### 미리보기로 한 번 더 확인

`prepare_listing` 은 준비가 끝나면 prepared payload 와 **같은 디렉터리**에
`preview.html` 파일을 쓴다(경로는 반환에 `preview_path` 로 들어있다). 이 파일은
외부 리소스(CSS/JS/이미지/웹폰트)를 일절 불러오지 않는 단일 HTML 이다 — 로컬에서
`file://` 로 열어도 어떤 네트워크 요청도 일으키지 않는다. 상세페이지는 iframe 의
`srcdoc` 으로 끼워넣어 실제 렌더 결과를 그대로 보여준다.

미리보기에는 **고시 정보 표**가 있다. 각 필드값이 어디서 왔는지 출처를 함께 표시한다:

- **사용자 입력** — 판매자가 직접 준 값
- **설정 기본값** — `.local/config.json` 의 `smartstore_notice_defaults` 에서
  자동으로 채워진 값. 의도한 값인지 확인해야 한다
- **미제공** — 비어 있어 등록 단계의 컴플라이언스 검사가 요구하면 거부되는 필드

**정직한 한계**: 이 파일은 판매자가 직접 눈으로 확인하는 화면일 뿐이다. "사진이 실제
상품과 일치하는지", "문구가 자연스러운지", "옵션 구성이 적절한지"는 기계가 잡지
못한다. 아래 승인 게이트는 **선언 게이트**다 — `preview_confirmed=True` 로 회신하는
것은 "봤다"는 선언일 뿐, 실제로 봤는지 우리는 알 수 없다. 원본 사진 게이트와 같은
성격이다.

**직접 편집(클립보드 다리)**: 상품명·판매가·고시 표의 값 칸·검색태그는 페이지에서
**직접 고칠 수 있다**. 정확한 값을 이미 아는 수정(예: "상품명을 ○○로")은 대화로
감싸는 것보다 직접 타이핑이 빠르다. 고친 뒤 **[수정사항 복사]** 버튼을 누르면
바뀐 필드만 모아 클립보드에 담긴다 — 그걸 **채팅에 한 번 붙여넣으면** 모델이 명시
인자로 재호출한다. `file://` 페이지는 서버로 되돌아갈 수 없기 때문에, 이 화면에서
고친 것만으로는 **반영되지 않는다**(화면에도 이 안내가 나온다).

`register_product` 는 설정의 `require_preview_confirmation` 이 켜져 있을 때(기본 켬)
`preview_confirmed=True` 가 아니면 등록을 거부하고 미리보기 파일 경로를 사유에
담는다(네이버 호출 0회). 100건씩 올리는 판매자는 설정에서 이 게이트를 끌 수 있다.

### 로컬 승인 다리(선택, 기본 꺼짐)

설정의 `enable_local_approval` 을 `true` 로 켜면, 등록 도구가 승인 대기 모드로
풀렸을 때 **로컬 포트 하나**를 열어 미리보기의 [승인] 버튼이 실제로 동작하게 한다.
포트를 열지 않는 경로(클립보드 복사 → 채팅 붙여넣기, 대화로 승인)는 그대로다 —
이 설정이 꺼져 있으면 포트가 열리지 않으며 아무것도 바뀌지 않는다.

**동작**: 승인 대기 모드에 들어가면 (1) 일회용 토큰을 발급하고, (2) `127.0.0.1`
의 자동 할당 포트에서 대기 서버를 띄우고, (3) 미리보기 파일을 그 포트를 가리키도록
갱신한다. 브라우저에서 [승인] 이나 [수정 후 승인] 을 누르면 페이지가 로컬 포트로
POST 하고, 토큰이 맞으면 등록이 진행된다. **10분**이 지나면 자동으로 만료되어
포트가 닫히고 등록은 일어나지 않는다.

**왜 기본 꺼짐인가**: 같은 컴퓨터의 **다른 웹페이지**도 그 포트를 찌를 수 있다.
악성 사이트가 사용자 모르게 승인을 눌러 상품을 등록하는 것을 막기 위해, 이 서버는
10중 방어를 갖추고 있다:

1. `127.0.0.1` 에만 바인드(외부 컴퓨터 접근 불가)
2. 승인 대기마다 새 일회용 토큰(`secrets.token_urlsafe`, 32바이트 이상) —
   `secrets.compare_digest` 로 일정 시간 비교(타이밍 공격 차단)
3. 1회 소진 — 성공한 토큰은 즉시 폐기, 재사용 거부
4. 10분 수명 제한 — 만료 시 서버 종료
5. `Origin`/`Referer` 검사 — `null` 또는 `file://` 만 허용
6. **`Access-Control-Allow-Origin` 헤더를 절대 내보내지 않는다** — 내보내면
   악성 페이지가 응답을 읽을 수 있다
7. 해당 `product_key` 1건만 처리(다른 상품·다른 동작 불가)
8. 설정 기본 `false` — 켜야 동작
9. 처리 후 또는 만료 시 반드시 서버 종료(좀비 포트 금지)
10. 로그에 토큰을 찍지 않는다

**정직한 한계**: 토큰이 유출되면(예: 악성 프로세스가 로컬 파일을 읽은 경우) 이
방어 중 일부가 무의미해진다. 로컬 승인은 **편의** 기능이며, 켜지 않아도 클립보드
경로와 대화 승인으로 등록 흐름이 온전히 동작한다.

### 무엇을 되묻는가

**막히면 그 자리에서 "필요한 전부"를 한 번에 알려준다.** 사진이 없어서 거부돼도
응답의 `requirements` 에 그 시점에 알 수 있는 것이 같이 실린다 — 카테고리 후보(점수 포함),
그 카테고리군에서 반드시 필요한 고시 항목, 후보별 추가 요구, KC 대상 여부, 원산지·A/S
설정 상태, 이미지 요건. 그래서 되묻는 왕복이 한 번으로 끝난다.

- `category.needs_category_choice` 가 참이면 **카테고리를 임의로 정하지 말고**
  후보를 사용자에게 보여 고르게 하라. 고시 요구는 카테고리에 따라 달라진다.
- `notice_required_fields.is_complete` 가 거짓이면 그 목록은 **아직 전부가 아니다** —
  카테고리 확정 전에는 완료로 취급하지 마라.
- `certain_one_of` 의 각 묶음은 **둘 중 하나만** 채운다(둘 다 채우면 네이버가 거절한다).

**뭘 팔든 공통으로 묻는 5가지**:

| 묻는 것 | 이렇게 답하면 된다 |
|---|---|
| 반품/교환 배송비 | 단순변심 왕복 6,000원 / 상품 하자 시 판매자 부담 |
| 청약철회 제한 사유 | 착용 흔적이나 세탁 후에는 반품 불가 |
| 품질보증 기준 | 소비자분쟁해결기준에 따름 |
| 소비자 피해보상 절차 | 고객센터 접수 후 3영업일 내 안내 |
| 불만처리 및 분쟁해결 기준 | 고객센터 010-0000-0000 |

카테고리에 따라 더 묻는다. 의류면 소재·색상·치수, 식품이면 보관방법·소비기한 같은
것들이다. 어떤 카테고리가 무엇을 요구하는지는 `src/clossify/data/notice_types.json`,
필드 이름의 한국어 표기는 `src/clossify/data/notice_field_labels.json` 에 있다.

**아직 한국어 이름이 없는 필드는 영어 그대로 나온다** (전체 123개 중 84개).
그럴듯한 번역을 지어 붙이지 않기 때문이고, 공식 문서에서 확인되는 대로 채워진다.

### 매번 묻지 않게 하기

원산지·제조사·수입사·모델명·AS 전화, 그리고 **위 공통 5가지**(반품/교환 배송비,
청약철회 제한 사유, 품질보증 기준, 소비자 피해보상 절차, 불만처리 및 분쟁해결
기준)는 `.local/config.json` 의 `smartstore_notice_defaults` 에 한 번 넣어두면
다시 묻지 않는다. 공통 5가지의 키 이름은 고시 필드명 그대로(`returnCostReason`/
`noRefundReason`/`qualityAssuranceStandard`/`compensationProcedure`/
`troubleShootingContents`)다.

코드가 이 값을 지어내지는 않는다. config 에 빈 문자열이나 공백만 있으면
미설정으로 취급하여 상품마다 사용자에게 묻는다(기존 동작 유지). 단, **상품 입력에
해당 값이 있으면 그 값이 우선**한다.

**설정에서 채워진 값은 조용히 딸려가지 않는다.** 공통 5가지 중 config 에서 채워진
항목은 페이로드 빌드 결과 메타의 `notice_filled_from_config: [필드명...]` 에
명시된다 — 카테고리마다 달라야 하는 문구가 옛 값 그대로 딸려가면 잘못 신고되므로,
묻지 않고 채워진 값이 무엇인지 항상 보고한다.

### 조심할 것 — 이름이나 가격을 바꿨으면 준비부터 다시

준비 단계와 등록 단계는 **상품명과 가격으로 서로를 찾는다**. 준비한 뒤에 상품명이나
가격을 바꾸면 준비해둔 것을 못 찾고, **검수 결과가 조용히 무시된 채** 기본 검사만
돌아간다. 오류가 안 나서 알아채기 어렵다. 바꿨으면 "다시 준비해줘"부터 하면 된다.

### 등록한 뒤

> **"방금 등록한 거 네이버에서 다시 조회해줘"**

등록된 내용을 네이버에서 그대로 읽어와 확인한다.

> **"지금 팔고 있는 것들 보여줘"**

이 도구로 등록한 상품 목록을 상태와 함께 가져온다(보기 전용 패널 포함).

> **"'겨울 기모 후드티' 판매 잠깐 중지해줘"** → 확인을 되물은 뒤 `confirm` 으로만 실행

판매중지/재개는 등록 기록의 표식으로 대상을 특정한다 — 이름이 비슷한 다른 상품을
추측으로 건드리지 않는다. 확인 없이 실행하지 않는다.

> **"검수에 걸린 거 있는지 봐줘"**

네이버 검수 지적을 조회한다. 지적 0건 / N건 / 조회 실패(사유)를 구분해 보여준다.

### 통하지 않는 말

| 이렇게 말하면 | 이렇게 된다 |
|---|---|
| "사진 없이 상세페이지만 만들어줘" | 거절. 원본 사진 최소 1장이 진입 조건이다 |
| "고시 값은 적당히 알아서 채워줘" | 거절. 신고값을 지어내지 않는다 |
| "검사 통과한 걸로 처리해줘" | 안 된다. 결정론 검사 결과는 대화로 뒤집을 수 없다 |


## 설계 원칙

1. **로컬 실행·BYO-key** — 자격증명이 사용자 PC를 벗어나지 않는다. 서버 호스트 없음.
2. **결정론 검증은 서버가 담당** — 클라이언트 LLM이 관대해도 서버 코드가 막는다
   (fail-closed).
3. **사실을 지어내지 않는다** — 소재·치수·인증번호처럼 사용자만 아는 값은 요구하고,
   추정해 채우지 않는다. 빈 값은 빈 값으로 보고한다.
4. **범용 카테고리** — 품목을 가정하지 않고 카테고리/고시 데이터로 판정한다.
5. **원본 사진 최소 1장** — 원본 사진이 최소 1장 없으면 등록을 진행하지 않는다.
   존재하지 않는 상품의 판매글이 도구로 만들어지는 것을 막기 위한 진입 조건이다.
   **다만 본 도구는 사진의 진위나 출처를 검증하지 않으며, 등록 내용의 최종 책임은
   판매자에게 있다.**

### 필수 실값(경고)

아래 값은 **판매자가 실제 신고하는 진짜 값**이어야 한다. 안내문구/플레이스홀더
(`상세참조`/`상세페이지 참조`/`해당없음` 및 공백·표기 변형 포함)를 넣으면
컴플라이언스 게이트가 등록을 거부한다(fail-closed, 조용한 기본값 없음). 단,
사용자가 명시적으로 입력한 안내문구 값은 payload 에 그대로 전송된다(전송과
판정은 분리).

- `smartstore_notice_defaults.origin_area_code` / `origin_content` — 원산지
- `smartstore_notice_defaults.manufacturer`/`importer`/`model_name` — 해당 시
- `smartstore_notice_defaults.as_tel` — AS 전화번호(실번호). 정본 위치. `brand.as_tel` 은 에이전트 문서 `{AS_TEL}` 치환용이며 비어있으면 정본을 참조
- `kc_declaration.kcCertifiedProductExclusionYn` / `kcExemptionType` — KC 인증 대상 카테고리

### 고시 필드 미루기(명시적 선택)

네이버 스마트스토어에서는 고시 필드값을 "상세페이지 참조" 로 채우는 것이 일반적이다.
본 도구의 컴플라이언스 게이트는 빈 값과 안내문구를 같은 "없는 값" 으로 취급해
등록을 차단한다(조용한 자동 채움을 영구히 금지하기 위함). 다만 판매자가 **명시적으로
선택**한 경우에 한해, 특정 고시 필드를 "상세페이지 참조" 로 미룰 수 있다.

`register_product` 의 `deferred_notice_fields` 인자가 그 선택지다. 리스트로 필드명을
건네면:

- 게이트는 그 필드들을 "고시 필수필드 누락" 위반에서 **제외**한다. 빈 칸으로 남겨서
  자동 실패하는 일은 막되, 실값 검사(원산지·KC 등)는 그대로 둔다.
- 빈 자리에 한해 `상세페이지 참조` 표준 문구를 채워 전송한다.
- **실값이 있는 필드는 덮어쓰지 않는다** — 미루기로 이름만 올렸더라도 실값이 우선한다.
- 반환의 `deferred_notice_fields` 에 **실제로 미루기가 적용된** 필드명만 올라간다.
  실값이 있어 적용되지 않은 필드는 빠진다(조용한 적용 금지).

**원산지 필드는 미룰 수 없다.** 원산지(`made_in`/`originAreaInfo.content` 등)는
법적 선언이므로 `deferred_notice_fields` 에 넣으면 등록 자체를 거부한다(네이버 호출
0회, 거부 사유에 어느 필드가 문제인지 명시). 부분 적용도 하지 않는다 — 원산지가
섞여 있으면 전체 요청을 거부한다.

이것은 **기본값이 아니다**. `deferred_notice_fields` 를 주지 않으면 기존과 같이
빈 칸은 차단된다. 판매자가 "이 필드는 상세페이지로 미루겠다" 고 **알고** 선택했을
때만 작동한다.

### 낡은 고시 템플릿 — 인증 정보가 있는 고시 템플릿은 한 번 재저장해야 한다

`certificateDetails`(인증 정보) 같은 고시 값을 쓰는 상품군의 템플릿 가운데,
정본 필드명으로 인증 정보를 싣게 고치기 **이전에 저장된 것**은 인증 정보가 통째로
빠진 채 저장돼 있다. 마이그레이션 절차가 없어 재저장 전까지 그 템플릿으로 만드는
신규 상품마다 인증 정보가 계속 누락된다. 이 사실은 **도구가 알려준다** — 해당
템플릿을 적용하면 결과의 `stale_template_notice`(그리고
`template_applied.stale_certificate_details`) 에 "이 템플릿을 다시 저장하면
해소된다" 는 안내가 뜬다. 도구는 값을 자동으로 채우지 않는다. 인증 정보를 안 쓰는
고시 타입의 템플릿이나, 이미 인증 정보가 들어 있는(재저장된) 템플릿에는 이 안내가
뜨지 않는다.

## 개발자용

> **ruff 버전 주의**: CI(`.github/workflows/ci.yml`)는 `ruff==0.6.9` 로
> 고정되어 있다. 로컬에서 상위 버전을 쓰면 셀렉터 해석 차이로 "로컬은 통과, CI 는
> 실패"가 발생한다(실제로 `ISC004`/`RUF059` 셀렉터가 상위 버전에만 있어 0.6.9 에서
> 설정 파싱이 exit 2 로 실패한 사례가 있었다). 반드시 CI 와 **동일한 버전**을 설치할
> 것. 아래 명령으로 개발 의존성을 설치하면 `pyproject.toml` 의
> `[project.optional-dependencies] dev` 에 `ruff==0.6.9` 가 고정되어 있다.

### 커밋 전 검증 — `scripts/verify_local.py` 한 번이면 충분

개별 린트/테스트 명령을 따로 돌리지 말고 **이 스크립트 하나**를 돌린다. CI 가
실행하는 검사(`ruff check`·`ruff format --check`·`pip install -e ".[dev]"`·
`pytest -q`·`python scripts/scan_repo.py`)를 **같은 순서로 그대로** 실행하므로,
이 스크립트가 exit 0 이면 CI 도 녹색이다. 하나라도 실패하면 exit 1 이며 어느
단계에서 깨졌는지 바로 보인다. ruff 버전이 CI 와 다르면 경고를 출력한다.

```sh
pip install -e ".[dev]"            # ruff==0.6.9 포함 개발 의존성 설치
python scripts/verify_local.py     # 커밋 전 이것만 돌리면 CI 와 같은 검사를 한다
```

> 이 스크립트와 `.github/workflows/ci.yml` 은 한 쌍이다. 워크플로를 바꾸면
> 스크립트도 함께 바꾼다(스크립트 상단 주석에 같은 안내가 있다).

### 1차 방어선 — `pre-commit install` 을 **한 번은** 해야 한다

`.pre-commit-config.yaml` 은 커밋 직전 gitleaks(평문 키)·ruff-format·개인키 탐지를
돌리는 설정이다. **설정만으로는 아무 일도 일어나지 않는다** — git 훅을 설치해야 실행된다.
설치를 빠뜨리면 커밋이 그냥 통과하므로 방어선이 있다고 착각하기 쉽다(실제로 그런 상태였다).

```sh
pip install -e ".[dev]"     # pre-commit 포함
pre-commit install          # .git/hooks/pre-commit 생성 — 이걸 해야 돈다
pre-commit run --all-files  # (선택) 지금 트리 전체에 한 번 돌려보기
```

훅이 설치됐는지는 `.git/hooks/pre-commit` 파일 존재로 확인한다.
1차(pre-commit, staged 만)와 2차(CI, 전체 트리)는 한 쌍이며 **둘 다 있어야** 한다.

자세한 설계·모듈 의존·데이터 자산은 `docs/ARCHITECTURE.md`, 배경 결정은 `docs/adr/` 참고.
