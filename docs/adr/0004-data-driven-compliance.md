# ADR-0004: 데이터 기반 컴플라이언스 검사

- **상태**: 승인
- **날짜**: 2026-08-03

## 배경

초기 구현은 고시(`productInfoProvidedNoticeType`) 타입을 `ETC`/`FURNITURE` 2종만
알고 있었고, 규제 신고값인 원산지와 KC 인증 면제 여부를 **코드에 하드코딩**해
판정했다(예: 원산지가 특정 국가면 FAIL, 특정 면제 코드면 통과).

이 방식의 문제:

1. **품목 가정**: 2종만 알면 의류·신발·가전·식품 등 다른 카테고리의 필수 필드를
   검사할 수 없다. 사용자가 무엇을 파는지 코드가 가정하게 된다.
2. **허위 신고 위험**: 규제 신고값(원산지·인증면제)을 엔진이 추정해 채우거나,
   판매자가 빈 칸을 둔 채 등록되면 **허위 신고**가 네이버에 그대로 넘어간다.
3. **규정 대응 경직**: 규정이 바뀌면 코드를 수정해야 한다.

## 결정

1. **카테고리·고시 데이터를 저장소에 둔다**(`data/category_meta.json`,
   `data/notice_types.json`, `data/certification_types.json`). 이 데이터를 기준으로
   컴플라이언스를 판정한다(데이터 기반). 코드가 품목을 가정하지 않는다.
2. **규제 신고값(원산지·KC 인증 정보)은 판매자 config 필수**. 미설정 시 등록을
   거부한다(**fail-closed**, 조용한 기본값 없음). 빈 값은 빈 값으로 보고한다.
3. **어떤 값도 추정해 채우지 않는다**. 소재·치수·인증번호처럼 사용자만 아는 값은
   `needs_user` 요청으로 되물어지며, 엔진이 임의 값을 만들어 넣지 않는다.
4. 고시 필드 검사는 타입별 **공통 5개 + 타입별 고유 필드** 구조(`notice_types.json`
   의 `node`/`fields`)를 따른다. 카테고리 경로에서 고시 타입을 추론해 올바른
   필수 필드 목록을 적용한다.
5. 원산지 판정은 "config 값과 payload 값이 일치하는가"만 본다(특정 국가값을
   하드 단정하지 않는다). KC 판정은 `category_meta.requires_kc()` 기준만 본다.

## 결과

- **범용 카테고리 지원**: 특정 품목 코드 경로 없이 데이터로 임의 카테고리 검사.
- **허위 신고 원천 차단**: 추정값·조용한 기본값 금지 + 미설정 시 등록 거부로,
  규제 신고값이 빈 채 넘어가지 않는다.
- **데이터 갱신만으로 규정 대응**: 규정 변화 시 `data/` 파일을 갱신하면 코드 수정
  없이 검사 기준이 따라간다(`scripts/fetch_category_meta.py`).
